finding (optional): `tools/f64_diff.py` has a reproducible CPU divergence for an f64 clamp of a -0 result, now only covered by the default exclusion

Where: `tools/f64_diff.py`, known case `f64-clamp` (`make_case`, the `v_add_f64 ... clamp` branch). Why it matters: `v_add_f64 v[8:9], v[8:9], v[10:11] clamp` with both operands -0.0 gives reference words (0, 0) and translator/CPU-interpreter words (0, 0x80000000), because `FClamp(-0.0, 0, 1)` is not specified to give +0 and the interpreter keeps -0 (`tests/spirv_interp.py`, `FClamp`). The hardware result for f64 is unmeasured; `docs/shader_validation.md` records clamp of -0 as +0 for f32 and f16. The known case was kept as a NaN case (which agrees) because a -0 case makes #1112's `tests/test_f64_diff.py` (asserts exactly one "MISMATCH:" under `--known`) fail on whichever PR lands second. Fix once #1112 and #1366 are in: retarget the `--known` clamp case to -0 operands (entry `f64-clamp-neg-zero`) and either make the translator select +0 for a -0 result or document it as driver-defined. Needs hardware: only to confirm the f64 -0 word.

finding: `v_swap_b32` (tools/rdna2spirv.py:8978-8985) does not validate its operands, so forms the assembler rejects translate silently
- Where: the `elif op == "v_swap_b32":` branch reads both operands with `self.src_u(...)` and writes both with `self.dst(...)`, with no operand-kind or modifier check (upstream/main 507029d1).
- Verified on 507029d1 with `tests/semantic/support.translate_lines` + `mrt0_words` (v0 = 1, v4 = 2): `v_swap_b32 v4, -v0` gives words (2, 0x80000001), the source `neg` is applied to the value swapped into v4; `v_swap_b32 v4, s0` translates (SGPR source accepted); `v_swap_b32 s4, v0` translates and silently writes SGPR s4 through `dst`; `v_swap_b32 v4, 1` is refused with the misleading `Unsupported: destination imm` (it comes from `Gen.dst` at line 1702 and names no instruction).
- Why it matters: little in practice. `llvm-mc -mcpu=gfx1036` (LLVM 18) rejects every one of these ("invalid operand for instruction"; `-v0`: "not a valid operand"; also `clamp`, `v[4:5]`, a literal, `_dpp`, `_sdwa`), so neither the assembler nor the repo's disassembler can produce them; it only affects hand-written input, which gets a wrong result instead of a refusal. The fix would be a short check that both operands are plain VGPRs with no abs/neg/sext/modifier, refusing with `v_swap_b32 operand`, plus a test per form.
- Needs no hardware and no game files.
